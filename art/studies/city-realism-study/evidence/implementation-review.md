# City reference implementation review

Date: 2026-09-10. Stage: interactive reference in progress. Approval: pending. This is not completion of the full city plan.

## Implemented

- An explicit City preview tab in the existing Agents view, lazily loaded. The existing island/ledger preference is preserved; preview selection does not overwrite it.
- A 1800 by 1200 metre ground envelope, a 600 by 400 metre reference district, two stations and two functional building links. Three distant districts are labelled blockouts, not completed districts.
- Explicit layered graph, ground paths, station lift links and an elevated crossing. A demo control exercises the bridge route. Reference plots support four-metre adjustments within footprint and access constraints, for the current session only.
- Time-based physical train movement, eight reserved passenger slots, waiting, boarding, riding, exiting, walking and arrival. Slot reservations remain until disembarkation. Existing checkpoint updates replace journey intent without moving the actor instantaneously. Stale updates are ignored.
- Separate actual work-state and physical-journey displays. Live checkpoints are grouped into two reference destinations; no new backend event schema or tool-execution gate was introduced. Idle/cancelled activity settles toward a local destination rather than maintaining an obsolete task target.
- Demo population choices of 1, 8 and 30. These agents never submit commands or modify the backend roster.
- Continuous orbit/zoom and close follow, automatic 30-minute day cycle, manual time and pause, theme-token overlays in English/German/Spanish. Existing reduced-motion, visibility and WebGL lifecycle hooks are reused.
- Editable Blender source, a reproducible authoring script and five manifest-exported GLBs: station, building, train, tree, reference citizen. The citizen has authored transform-animation tracks. It is not yet a replacement for a production skinned figure or its fit contract. Static reference structures merge geometry by material to reduce draw calls.

## Performance and platform limits

Observed browser device: Windows, Chrome/WebGL via NVIDIA RTX 5070 Ti. The initial canvas was 2014 by 1165 in a 2560 by 1249 viewport with five live agents. A 1366 by 768 viewport was also inspected. Before batching, an observed live scene used 565 draw calls; after batching, an observed one-demo scene used 187, while a thirty-demo scene used 534. Populations differ, so these are observations rather than a controlled improvement percentage.

Browser frame pacing varied between background-like 1–2 FPS readings and a 47 FPS observation after bringing the tab forward. This session has not established a controlled frame-time benchmark. No integrated-GPU hardware was available. The specified 30 FPS target is therefore UNVERIFIED, not passed. GPU memory, frame-time percentiles, cross-platform and full WebView performance remain to be measured.

A 45-frame diagnostic at 1366 by 768 with thirty demo agents, before distant-figure simplification, recorded median 13.9 ms, p95 527.9 ms and mean 136.16 ms. This fails to demonstrate stable frame pacing. After adding distant figure proxies and avoiding repeated idle animation updates, the thirty-agent overview used 204 draw calls and 54,496 triangles; captures showed 41–46 FPS at some moments and 1–3 FPS at others. The lower draw count is verified; the frame-pacing issue is still unresolved. A brief local-server connection refusal interrupted testing; the listener returned and verification resumed in a fresh tab. No desktop restart was issued by this task.
