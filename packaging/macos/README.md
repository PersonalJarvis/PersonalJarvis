# macOS packaging — the .dmg

`packaging/macos/build.sh` produces one downloadable disk image per processor
family:

| Runner | Artifact |
|---|---|
| Apple Silicon (`macos-15`) | `dist/installers/PersonalJarvis-macOS-arm64.dmg` |
| Intel (`macos-15-intel`) | `dist/installers/PersonalJarvis-macOS-x64.dmg` |

The image contains `Personal Jarvis.app` next to a symlink to `/Applications`:
open it, drag the app across, done. The app is a PyInstaller `BUNDLE` built
from `jarvis.spec`; its icon is `assets/icons/jarvis.icns`, regenerated by
`packaging/macos/make_icns.py`.

## Building

```bash
python3 -m pip install -e ".[full]"
python3 -m pip install pyinstaller
bash packaging/macos/build.sh
```

`DRY_RUN=1` prints every command it would run without running any of them,
which is how the flow is rehearsed off a Mac.

## Signing and notarization

All four settings come from the environment, so the same script serves a
maintainer's Mac and both GitHub runners:

| Variable | Meaning |
|---|---|
| `APPLE_SIGNING_IDENTITY` | `Developer ID Application: NAME (TEAMID)` |
| `APPLE_ID` | Apple ID used for notarization |
| `APPLE_TEAM_ID` | 10-character team identifier |
| `APPLE_APP_SPECIFIC_PASSWORD` | app-specific password for that Apple ID |

With the identity set, the script signs every nested Mach-O object inside the
bundle before sealing the bundle itself (Apple's guidance is inside-out;
`--deep` on the outer seal is the safety net, not the strategy), using
`--options runtime --timestamp` and `packaging/macos/entitlements.plist`. It
then notarizes **the app** before building the image, so the ticket is stapled
into the bundle and survives the user dragging the app out of the `.dmg` -
otherwise the first launch after that drag needs a network round trip. The
image is signed, notarized and stapled afterwards, then `hdiutil verify` and
`stapler validate` check the result.

The app-specific password is never written to the build log: the `notarytool`
line is printed with the secret replaced and the real invocation is not traced.

Without `APPLE_SIGNING_IDENTITY` the script **ad-hoc signs**
(`codesign --force --deep -s -`), skips notarization, and says so in one line.
That build is fine for local testing and must not be published.

## First launch

* **Signed and notarized build:** a normal double-click. Nothing to explain.
* **Unsigned or ad-hoc build:** macOS refuses the first double-click
  ("Personal Jarvis can't be opened because Apple cannot check it for malicious
  software"). The way through is **right-click (or Control-click) the app in
  Finder, choose Open, then Open again in the dialog**. macOS remembers the
  decision for that copy of the app. Alternatively
  `xattr -dr com.apple.quarantine "/Applications/Personal Jarvis.app"`.

## Permission prompts

macOS grants privacy permissions to an *app identity*, not to a folder, and
Apple does not let an installer pre-approve any of them. The app therefore asks
for each one at the moment it needs it, through Apple's own prompts:

* **Microphone** — voice input; the app is usable for text without it.
* **Speech recognition** — on-device dictation.
* **Camera** — only the vision features.
* **Screen recording** — screen capture and Computer-Use; granted in
  System Settings > Privacy & Security, and macOS requires a restart of the app
  afterwards.
* **Accessibility / Input monitoring** — global hotkeys and Computer-Use input.
* **Automation (Apple events)** — controlling other apps, e.g. the media
  session.

Each of these needs *both* an entitlement in
`packaging/macos/entitlements.plist` and a usage-description string in the
bundle's `Info.plist` (built by `jarvis.spec`). Missing entitlement: the app is
refused before the prompt appears. Missing usage string: macOS kills the app
the moment it asks. Declining any of them leaves the app working, with that
feature honestly unavailable.

## Reaching the CLI

The bundle ships the console entry at
`Personal Jarvis.app/Contents/MacOS/jarvis`. It is the same program as the
pip-installed `jarvis` command:

```bash
"/Applications/Personal Jarvis.app/Contents/MacOS/jarvis" --version
"/Applications/Personal Jarvis.app/Contents/MacOS/jarvis" serve
```

To type plain `jarvis`, link it once:

```bash
sudo ln -sf "/Applications/Personal Jarvis.app/Contents/MacOS/jarvis" /usr/local/bin/jarvis
# or, without sudo, if ~/.local/bin is on your PATH:
mkdir -p ~/.local/bin
ln -sf "/Applications/Personal Jarvis.app/Contents/MacOS/jarvis" ~/.local/bin/jarvis
```

The symlink keeps working across updates because the app bundle is replaced at
the same path. Run the CLI through the **bundle**, never through a copy of the
executable moved elsewhere: macOS ties privacy grants to the bundle identity,
and a launch from outside it is a different identity with no grants.

## How an update replaces the app

The in-app updater downloads the `.dmg` for this Mac's architecture from the
GitHub Release, verifies it against `installers-SHA256SUMS.txt` from the same
release, mounts it with `hdiutil attach`, replaces the running
`Personal Jarvis.app` atomically, detaches the image and relaunches with
`open`. Because the bundle identifier does not change, the privacy grants the
user already gave survive the update - that is the entire reason every launch
path has to enter through one bundle identity.

## What has NOT been verified

Nobody has run this script on a Mac yet. What has been checked:
`bash -n`, ShellCheck 0.11.0 at `-S style` with zero findings, and a full
`DRY_RUN=1` rehearsal of both the unsigned and the signed/notarized path,
including a check that the app-specific password never reaches the output.

A real run - PyInstaller on macOS, `codesign`, `notarytool`, `hdiutil`,
Gatekeeper on a downloaded image, and the permission prompts - needs the macOS
CI job or a physical Mac and is the last gate before the first public macOS
release.
