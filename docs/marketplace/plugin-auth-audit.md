# Plugin authentication and end-to-end audit

RUB-94, observed 2026-09-12. **Acceptance incomplete: 46 plugins attempted through the real UI, 0 full PASS, 46 BLOCKED, 0 unexplained FAIL.** Every plugin has a final PASS/BLOCKED classification for the current attempt, but the complete connection and lifecycle acceptance criteria are not satisfied. Do not close the ticket on this evidence.

This inventory supersedes earlier claims that mocked DCR checks proved working logins. Source configuration is `jarvis/marketplace/seed_catalog.json`; the companion [machine-readable audit](plugin-e2e-audit.json) binds each row to its current auth and execution configuration using `config_fingerprint` from `scripts/ci/check_plugin_auth_contract.py`.

## Evidence boundaries

Every catalog plugin has an observed Connect or Reconnect entry. A stage-level `ui: PASS` means the UI attempt was observed, not that Add, installation or connection completed. A stage-level `browser: PASS` means an official provider page was reached, not that authorization succeeded. No plugin has verified successful callback, new connected state, real functional smoke test, complete disconnect/reconnect, or post-restart persistence in this audit.

Eleven existing connections were preserved: github, gmail, google_drive, google_calendar, youtube_music, youtube_studio, x, telegram, notion, cloudflare and linear. Their Reconnect controls were exercised without revoking working credentials. They were **not** tested from a clean, unconnected state. Existing credentials and existing Connected labels do not prove the new flow. The remaining rows describe connection attempts, not certified fresh installations.

The real runtime was exercised on Windows. Linux/macOS behavior and clean installation, update migration, refresh/expiry, consent denial, timeout/retry, disconnect and restart remain unverified unless a later dated observation explicitly replaces this statement. A partial network sample is not a complete error-free network audit. Automated contract tests are separate evidence and cannot promote a row to end-to-end PASS.

## Provider-specific interpretation and primary sources

- Vercel, Supabase and Stripe now use browser-primary hosted MCP authentication. The real UI reached official sign-in pages; this does not establish a completed grant or usable tool. See [Vercel MCP](https://vercel.com/docs/mcp/vercel-mcp), [Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp), and [Stripe MCP](https://docs.stripe.com/mcp).
- Home Assistant opens an address-only dialog before the instance's browser login. An instance address is an ordinary connection prerequisite. No access token is requested by that dialog. See [Home Assistant authentication API](https://developers.home-assistant.io/docs/auth_api/).
- Discord is a local bot channel. Its runtime bot credential and server installation are distinct from user OAuth login. See [Discord OAuth2 and permissions](https://docs.discord.com/developers/platform/oauth2-and-permissions). Telegram is likewise a Bot API channel; its token requirement is specific to this API, not every Telegram product. See [Telegram Bot API](https://core.telegram.org/bots/api).
- AgentMail onboarding requests a key from the existing account console and does not copy another tool's credentials. Its [quickstart](https://docs.agentmail.to/quickstart) documents account API keys. This is a documented integration limitation, not evidence that a browser login has been tested.
- Meta supports OAuth. The current connector's token-paste path does not meet the browser standard. The remaining publisher work is a confidential HTTPS callback/broker and required app review. The [archived official OAuth client implementation](https://raw.githubusercontent.com/facebookarchive/php-graph-sdk/5.x/src/Facebook/Authentication/OAuth2Client.php) demonstrates OAuth token exchange; it is historical evidence, not current approval of this project's app. Current Meta documentation could not be retrieved during investigation (HTTP 429), so unsupported-provider claims are not justified.
- Notion, Linear and Cloudflare reached official consent pages. Workspace/cloud-resource grants remain pending account-holder approval. Their pre-existing connections were preserved.
- Higgsfield initially returned `invalid_scope`. The scope-selection fix uses protected-resource scopes instead of the issuer-wide scope set. A new real UI Connect run reached the official [Higgsfield sign-in page](https://higgsfield.ai/de/auth/sign-in), inspected in the browser DOM, with `openid email offline_access`; the earlier error did not recur. This verifies the repaired sign-in entry, not successful authorization or a usable plugin. Account sign-in remains BLOCKED.

## Release and maintenance gate

Run `python scripts/ci/check_plugin_auth_contract.py` for configuration, matrix coverage and attestation integrity. Historical BLOCKED rows may pass this structural check only with concrete blocker evidence; that does not make them standard-ready. An unresolved FAIL is deliberately rejected. Run `python scripts/ci/check_plugin_auth_contract.py --require-e2e-pass` for strict release qualification; current evidence must fail qualification.

A new built-in plugin must carry a complete real journey PASS before release. Record a genuine functional action for smoke evidence; discovery or listing available tools is insufficient. An auth/execution configuration change invalidates the fingerprint and requires renewed relevant observations. Never refresh a fingerprint to disguise stale successful evidence.

For closure, complete all independently achievable repairs and replace each remaining external BLOCKED row only with new observed evidence or a precisely maintained external dependency. The ticket's acceptance criteria remain unsatisfied while clean-state, functional and lifecycle verification is missing. The audit itself must never be presented as completion of those checks.
