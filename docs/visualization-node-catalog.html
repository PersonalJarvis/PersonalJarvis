Run Graph — Node Catalog

Every node the Visualization section should be able to draw, rendered in the app's own tokens.

Why this document

The canvas is finished. The vocabulary is not.

VisualizationView.tsx already does the hard part: pan, anchored zoom, fit, edge routing, ports derived from real edges, a node inspector, and a no-JS server-rendered twin (mission_graph.py). What it lacks is things to draw. This file is the catalog: one card per node type, in the app's real colours, with the data source each one reads from — the seed for nodeSpec.ts and the backend that has to feed it.

Measured on this machine, 2026-08-13. The canvas reads only /api/outputs (archived mission worktrees): 17 runs, all from 16–17 May 2026, of which 9 have a worker stream. Across every one of those streams the complete set of tool names is Write (3×) and Read (1×) — so of eleven shipped node categories, nine have never had a single row of data. Meanwhile the session store holds 305 sessions, 458 turns and 8 929 events, and ROUTER_TOOLS exposes 33 real Jarvis tools — none of which toolCategory() currently recognises.

The catalog below is therefore split by data source, and every node says where its facts come from. A node without a source is a drawing, not a diagnosis.

Anatomy

What one node is made of

Today every category renders the same 216×76 rectangle: icon tile, two text lines, status dot. That is why a graph of thirty steps reads as a grid of identical grey cards. The proposal keeps the header, adds a payload slot and a meta footer, and gives four families their own silhouette — which is where n8n's glanceability actually comes from, not from colour.

  1. Category rail — 3 px of the family hue on the left edge. Sorts the card into its family before a word is read, and stays visible at 35 % zoom where icons blur out.
  2. Icon tile — one lucide glyph per family, on a 13 % tint of the same hue. Already implemented in nodeSpec.ts; unchanged.
  3. Title + detail — the tool name and the one line that identifies the call (command, path, query). Already implemented.
  4. Status dot — done / failed / running / no-confirmed-result. Already implemented, and honest: an uncorrelated call is never shown as success.
  5. Payload slot (new) — two lines of what actually happened: the diff, the stdout head, the result count, a thumbnail. This is the single biggest step from "a picture of a run" to "I can follow what it did".
  6. Meta footer (new) — the chips that carry the facts a table would hide: risk tier, approval source, exit code, attempts, tokens, cost, duration.
  7. Ports — dots only where an edge really attaches. Already implemented and derived from the edge set, so a dot can never lie. Gate nodes get two labelled outputs.

Nodes, by family

live already drawn today · extend exists but shallow or mis-classified · new needs a data path first. Every entry names the event kind or API field it reads, so the backlog falls out of the table.

States

The same node, four ways

Status is carried three times over — dot, border, and (on failure) the incoming edge — because a 6 px dot alone is not a glanceable alarm at fit-zoom. "No confirmed result" is its own state and never borrows the success colour: the stream simply never proved the call returned.

Palette

Fifteen hues, both themes

Eleven --viz-* tokens ship today in index.css. Four are proposed here. Saturation stays low on purpose: signal-yellow is the only loud voice in this product, so the node hues are quiet accents that sort rather than shout.

Assembled

One real turn, drawn with these nodes

A single voice turn — wake word, transcript, brain, risk gate, a shell command, a spawn into two workers, the merge, the answer, two deliverables — using nothing but cards from the catalog. This is the target picture for an ordinary Tuesday, not for the rare archived mission.

What has to happen, in the order that pays off
